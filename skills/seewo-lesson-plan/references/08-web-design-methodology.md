# 教学网站开发（网页制作）方法论 · 完整引擎

> 本文件是「教学设计综合专家」第 ⑧ 域「教学网站开发（网页制作）」的方法论全文，供 Agent 主文件在识别到用户有教育场景建站需求后，按需深入查阅。
>
> **定位**：一名服务教师、班主任、年级组、家委会的**教育场景网页设计专家**——用户完全不需要懂技术，只需用一句话说清「我想要一个什么样的页面」，专家就能把这句话转译成一份**结构清晰、模块完整、符合教育场景要求、可直接落地为真实静态网页**的设计方案：班级主页、课程学习网站、作品展示站、活动报名网站、随机点名/分组小工具等。
>
> **重要边界声明**：本域不套用电商落地页、企业官网的通用模板逻辑做教育网页；不承诺静态网页无法实现的服务端/数据库/后台能力；涉及学生照片、姓名、联系方式等信息时，主动提示未成年人信息保护要求，不默许「全网公开、无脱敏展示」。

## 一、设计哲学

教育网页和商业网页的根本区别，在于它服务的关系不是「商家—消费者」，而是「老师—学生—家长」这条教育关系链。设计的第一优先级永远是：

- 这个页面服务哪一种教育关系（班级归属感？自主学习？成果被看见？家校协同？课堂效率工具？）；
- 学生、家长看到这个页面时，应该感受到什么、能完成什么，而不是「看起来多酷」；
- 技术花哨程度必须让位于内容是否清楚、操作是否简单、信息是否安全。

**判断标准**：如果把页面里的动效和配色全部去掉，只剩下文字和按钮，这个页面还能不能让一个从没上过网的家长或学生顺利完成任务？能，才是合格的教育网页设计。

## 二、方法论① 需求澄清四问法（一句话需求 → 可执行页面简报）

用户往往只给一句话（「帮我做个班级主页」「帮我做个报名网站」），第一步永远不是直接设计模块，而是先用四个问题把需求「显影」：

| 问题 | 追问要点 | 目的 |
|---|---|---|
| **① 谁会看这个页面？** | 学生自己看？家长看？还是给校外访客/评委看？年龄段是小学低段/高段/初中/高中？ | 决定文案语气、字号、色彩、信息密度 |
| **② 谁会操作这个页面？** | 只有老师能编辑，学生/家长只能浏览？还是学生也能上传、留言、报名？ | 决定要不要设计「提交/互动」类模块，以及权限边界 |
| **③ 核心要完成什么任务？** | 是「展示」（看了就走）还是「操作」（要填表、要点名、要学习并检测）？ | 决定信息架构类型（展示型 vs 任务型） |
| **④ 会在什么设备、什么场景下打开？** | 家长多半用手机、老师多半用电脑投屏、学生可能在平板上做练习 | 决定内容优先级排序（见方法论⑥） |

**追加三问（视场景启用）**：

- 素材现状：有没有现成的照片/名单/课程资料，还是需要先给出「需要老师准备什么材料」的清单？
- 更新频率：一次性做完不再改，还是需要老师能反复自己更新内容（如每周换一次荣誉墙）？
- 是否涉及学生信息：是否会出现学生姓名、照片、报名信息、成绩等，一旦涉及即触发方法论⑦。

四问法产出的是一张**「页面设计简报」**，作为后续所有设计动作的起点。

## 三、方法论② 教育网站五型信息架构库

中小学场景下的建站需求几乎都能归入以下五种类型之一（也可组合，如「课程网站+报名模块」）。每一型都有典型结构、首屏原则和「教育目标」。

#### 型 1：班级主页型（展示 + 情感连接）

- **教育目标**：建立班级归属感与集体荣誉感，让学生/家长愿意反复回来看
- **首屏原则**：第一眼要能感受到「这是我们班」的氛围——班级口号/班徽/合照，而不是一段说明文字
- **典型结构树**：首页（班级氛围首屏）→ 班级公约 → 风采展示 → 荣誉墙 → 活动相册 → （可选）班级寄语/班主任的话

#### 型 2：课程学习网站型（结构化知识 + 自学支持）

- **教育目标**：让学生能按清晰路径自主学习，知道「学完了没有、学得怎样」
- **首屏原则**：第一眼要看到「整门课的地图」（章节结构/学习路径），而不是第一章内容直接铺满
- **典型结构树**：首页（课程地图：章节列表 + 学习进度概览）→ 第 N 章（知识点讲解/微课视频/随堂练习/本章小结）→ 学习方法说明 → 答疑/答案区（可选）

#### 型 3：作品展示互动型（UGC 上传 + 社区互动）

- **教育目标**：让「被看见」成为学习动力，同时把互动控制在健康、鼓励性范围内
- **首屏原则**：第一眼是作品墙（网格/卡片流），突出「多样性」而不是「排名」
- **典型结构树**：首页（作品墙：分类筛选 + 最新/精选切换）→ 作品详情页（内容+作者+点赞+留言）→ 我要投稿（上传入口 + 投稿须知）→ 使用说明

#### 型 4：活动报名型（表单 + 数据管理）

- **教育目标**：让家长/学生用最少步骤完成报名，让老师能清楚看到报名结果
- **首屏原则**：第一眼说清楚「这是什么活动、需要做什么、什么时候截止」，报名入口要突出但不急促
- **典型结构树**：首页（活动说明：时间/地点/内容/须知）→ 报名表单（时段选择 + 基本信息）→ 报名成功页（确认 + 后续提示）→ 名单查看区（面向老师，权限区分）

#### 型 5：功能小工具型（单一任务的效率工具）

- **教育目标**：把课堂上重复、繁琐、易引发公平争议的小任务自动化、可视化
- **首屏原则**：第一眼就能开始操作，不需要看说明（核心操作按钮必须显眼）
- **典型结构树**：工具首页（名单录入区 + 核心操作按钮）→ 结果展示区（带仪式感呈现）→ 历史记录区（保证公平可查）→ 设置区（规则开关）

## 四、方法论③ 教育模块库（20+ 可复用模块）

每一种教育网站，几乎都由以下模块以不同组合拼装而成。专家的日常工作就是「诊断场景 → 从模块库选模块 → 为每个模块定制内容要素」。

| 模块名称 | 模块用途 | 内容要素清单 | 教育设计要点 |
|---|---|---|---|
| 班级氛围首屏 | 建立第一印象与归属感 | 班徽/口号/合照/学期主题 | 用「我们」而非「本班」的第一人称语气；照片优先于文字 |
| 班级公约 | 呈现共同约定的规则 | 公约条目、制定过程说明 | 强调「共同制定」而非「老师规定」，条目具体可执行 |
| 风采展示 | 展示学生个人/小组风采 | 姓名/花名+照片+一句话介绍+特长标签 | 每个学生都要有位置，不能只展示「尖子生」，避免变相排名 |
| 荣誉墙 | 展示集体与个人荣誉 | 荣誉名称+获得时间+获得者+简短说明 | 集体与个人分区，个人荣誉覆盖面要广（进步奖、坚持奖等） |
| 活动相册 | 记录班级活动瞬间 | 分主题/分时间相册、照片说明文字 | 按「事件」而非「日期」分类；配文字胜过纯图墙 |
| 课程地图 | 呈现整门课的结构 | 章节列表+每章目标+完成状态标记 | 必须让学生一眼看到「学到哪了、还有多少」 |
| 知识点讲解区 | 呈现具体知识内容 | 概念说明+图示+生活化例子+关键结论 | 遵循「先直觉理解、再规范表达」，避免上来就术语堆砌 |
| 微课视频区 | 承载讲解视频 | 视频+配套文字要点+观看时长提示 | 视频旁必须配「文字版要点」，方便回顾与无法流畅播放场景 |
| 随堂练习/自测 | 检验学习效果 | 题目+即时反馈+错因提示 | 反馈要说明「为什么错」，建议提供 2-3 次重做机会 |
| 学习方法说明 | 教学生如何自学 | 图标+步骤化文字 | 面向从未自学的学生，语言具体到「动作」 |
| 作品墙 | 汇总展示学生作品 | 缩略图/文本预览+作者+分类标签+发布时间 | 默认「最新优先」而非「点赞最多优先」，避免马太效应 |
| 作品详情页 | 单个作品完整呈现 | 完整作品内容+作者简介+点赞+留言 | 作品与评论要有留白 |
| 投稿/上传入口 | 学生提交作品 | 上传按钮+格式说明+投稿须知 | 须知写清「作品会被谁看到、能不能撤回」 |
| 点赞组件 | 正向鼓励反馈 | 点赞按钮+点赞数（可选是否显示具体点赞人） | 默认「点赞不排名、不做全站榜」 |
| 留言/评论区 | 促进交流与反馈 | 留言输入框+留言列表+审核状态标记 | 必须设计「先审后显」或「关键词过滤」机制 |
| 活动说明区 | 说明活动信息 | 名称/时间/地点/内容/注意事项/联系方式 | 家长最关心的「花钱/准备东西/几点」必须前置加粗 |
| 报名表单 | 收集报名信息 | 姓名+联系方式+（可选）时段+备注 | 严格执行「最小信息量原则」 |
| 时段选择器 | 分流报名避免拥堵 | 时间段列表+每段剩余名额提示 | 名额透明化，显示「剩余 X 位」 |
| 报名成功确认区 | 确认与后续提示 | 报名摘要回显+后续须知+（可选）取消/修改入口 | 一定要有「回显确认」 |
| 名单看板 | 老师查看报名情况 | 报名列表+统计摘要+导出入口 | 需设计「谁能看」的权限边界 |
| 名单/名单录入区 | 工具类数据输入口 | 文本框/表格录入，支持批量粘贴 | 批量粘贴录入是刚需 |
| 结果展示区 | 抽人/分组结果呈现 | 抽中/分组结果+适度动效+「再抽一次」入口 | 呈现要有仪式感但不能太慢 |
| 规则设置区 | 配置工具运行规则 | 排除已点名单、分组人数、是否允许重复等开关 | 默认值要「教育友好」（如默认排除最近点过的人） |
| 历史记录区 | 保证过程公平可追溯 | 时间戳+抽中/分组结果历史列表 | 学生才不会质疑公平性 |
| 使用说明/操作引导区 | 让非技术用户会用 | 图标化步骤+一句话说明 | 是所有「任务型」页面的必需模块 |

**组合逻辑**：五型信息架构（方法论②）决定「用哪些模块、按什么顺序排列」；模块库（本节）决定「每个模块具体装什么内容」。

## 五、方法论④ 教育向互动组件设计规范

教育场景互动组件的目标不是最大化停留时长或社交曝光，而是保护学生自尊、保证公平、鼓励参与、防止滥用。

#### （1）点赞与留言组件

- **正向激励优先于社交曝光**：默认不做「点赞排行榜」「留言最多榜」；如确需排名（如投票评选），要明确告知规则并设置合理评选周期。
- **审核前置机制**：留言建议「先审后显」或至少配置「敏感词过滤 + 举报按钮」，防止校园网络欺凌、人身攻击、广告刷屏。
- **匿名与实名平衡**：允许学生用「花名/昵称」而非实名参与，降低网络暴力对个体的精确打击风险。

#### （2）报名表单组件

- **数据最小化原则**：只收集完成报名任务必需的信息。班级活动「姓名 + 联系方式 + 时段」通常已足够，不应额外收集家庭住址、身份证号等无关信息。
- **告知与同意前置**：表单开头应有一句简短说明「本次报名信息仅用于本次活动安排，由班主任统一查看」。
- **时段/名额透明化**：如涉及抢名额，显示「剩余名额」比隐藏更公平、更能降低家长焦虑。
- **修改与撤回通道**：允许填表人在截止前修改或撤回报名信息。

#### （3）随机点名 / 分组工具

- **真随机与可配置公平规则**：核心是「随机」，但允许配置公平性规则（如「排除最近 N 次被点过的人」）。
- **仪式感与效率平衡**：揭晓结果可有短暂悬念动效（滚动名单再定格），但耗时控制在几秒内。
- **公开可追溯历史记录**：保留本节课/本周的点名与分组历史，学生质疑时老师可翻看记录自证公平。
- **分组教育意图选项**：建议提供「随机分组」和「按名单顺序轮转分组」两种基本模式。

#### （4）进度与激励类组件（勋章、进度条、打卡等）

依据自我决定理论（SDT）三大内在动机来源设计：

| 内在动机 | 网页设计对应 | 示例 |
|---|---|---|
| 自主感（Autonomy） | 给学生可选择的路径与表达方式 | 作品提交允许「写作文/画画/拍照」多种形式 |
| 胜任感（Competence） | 可见的进步反馈，而非单纯对错判定 | 进度条显示「已完成 3/8 章」；练习错题给「为什么错」 |
| 归属感（Relatedness） | 强调集体与被看见，而非个体排名 | 荣誉墙覆盖多种荣誉类型；留言区鼓励同伴互评 |

**激励设计陷阱**：把进度条、勋章做成「催更/催学」压力工具（如公开显示「未完成名单」）会伤害后进学生自尊，应优先展示「已完成」正向名单。

## 六、方法论⑤ 学段视觉语言适配表

不涉及具体像素/CSS 值，只给设计方向：

| 学段 | 色彩基调建议 | 文案语气 | 信息密度 | 图标/插画风格 | 互动组件复杂度 |
|---|---|---|---|---|---|
| 小学低段（1-2 年级） | 明快高饱和、卡通化 | 简短、拟人化、多用称呼语气 | 极低，一屏一个重点 | 卡通拟人形象，图标能「看图猜意思」 | 极简，一步一按钮 |
| 小学中高段（3-6 年级） | 明快但略降饱和，允许主题色 | 亲切鼓励性，可用「同学们」 | 中低，每区聚焦一个内容 | 卡通与写实结合，可用班级 IP | 简单，允许 2-3 步操作 |
| 初中 | 清新有个性但不幼稚，可用潮流色 | 平实带活力，避免过度卖萌 | 中，可呈现结构化知识地图 | 简洁图标为主，减少卡通 | 中等，可接受表单/筛选/多步骤 |
| 高中 | 简洁克制专业感 | 理性直接、信息优先 | 中高，强调效率 | 极简线性图标 | 可接受较复杂功能性交互 |

> 家长向内容（报名说明、报名表单）应统一采用「清晰、正式、无歧义」语气，与学生向内容区分对待，即便在同一网站中。

## 七、方法论⑥ 响应式内容优先级排序法

这里说的「响应式」是**内容层面优先级排序**（不是技术自适应布局）：手机屏幕小、注意力碎片化，内容需按「必须第一眼看到」到「可以往下翻/进二级页面」分层。

**排序三步法**：

1. **列出该页面所有内容点**；
2. **按「完成核心任务是否必需」打分**：必需（如报名表单、截止时间）> 强化理解（如注意事项、活动流程）> 锦上添花（如往期照片、往期感言）；
3. **移动端首屏只放「必需」层，其余按优先级向下或折叠**，桌面端可适当并列更多「强化理解」层。

**交付要求**：设计蓝图中应明确标注每个模块的优先级（P0 必须首屏可见 / P1 首屏下方可见 / P2 可折叠或二级页面），而不是简单说「要适配手机」。

## 八、方法论⑦ 未成年人信息与内容安全 Checklist

依据《个人信息保护法》《未成年人保护法》《未成年人网络保护条例》《儿童个人信息网络保护规定》核心精神，转化为设计层面的可执行准则（专家把关内容设计，不代替法律咨询）：

| 检查项 | 设计准则 |
|---|---|
| 信息最小化 | 只收集完成任务必需信息；报名表单不问家庭住址、身份证号等无关字段 |
| 展示范围控制 | 学生照片、姓名默认只在班级内部/家长可见范围展示，避免「全网公开」默认选项；对外展示应有说明并建议事先取得家长知情同意 |
| 脱敏建议 | 涉及家庭信息、成绩排名等敏感内容时，建议用花名/学号/等级代替实名、具体分数公开展示 |
| 未满 14 周岁特别提醒 | 涉及收集不满 14 周岁学生个人信息时，应醒目标注需以显著方式告知监护人并取得同意，说明用途、留存期限，提供拒绝/撤回选项 |
| 留言/评论安全 | 必须有审核或过滤机制，防止网络欺凌和不良信息传播 |
| 数据留存与导出 | 活动/报名类信息应设计「活动结束后可删除/归档」提示，不建议长期公开滞留 |
| 内容适龄性 | 素材需符合学生年龄段心理发展，避免不适宜、可能引发攀比或焦虑的内容 |

> **角色边界**：本域在设计蓝图中会明确标注「此模块涉及学生信息，建议教师注意事项」，但不代替学校/机构履行合规审批责任。

## 九、方法论⑧ 「怎么用 / 怎么搭 / 怎么实现」说明产出法

教育建站用户普遍不是技术人员，「看不懂就等于用不了」。需针对三类人产出三种层次说明：

#### 第一层：给委托建站的老师看的「实现方式决策说明」（不涉及代码）

帮助老师理解「没有专门服务器/数据库时，实际能做到什么程度」，避免期望落差。以报名网站为例：

| 路径 | 适用情况 | 能力与限制 |
|---|---|---|
| 页面本地记录 + 手动导出/截图汇总 | 报名人数少、时间短、对实时后台无强需求 | 简单直接，但换设备/清缓存可能丢失数据，需及时导出保存 |
| 借助表单类工具嵌入（问卷/表单服务） | 需要稳定可靠地长期查看和统计 | 数据统一收集在服务方，更稳妥，但意味着数据经过第三方，需提前告知家长 |
| 由建站能力搭建更完整的数据存储方案 | 报名规模大、需长期管理、多场复用 | 功能更完整，但搭建和维护成本更高，适合长期使用 |

#### 第二层：给最终使用者（学生/家长）看的「页面内操作引导模块」

- **图标化 + 动作化短句**：用「① 点这里上传 → ② 写一句话 → ③ 点击提交」，而非「请按要求操作」；
- **就近原则**：说明放在对应功能旁或页面顶部固定位置；
- **图文并重**：点名工具、报名表单建议配简单示意图。

#### 第三层：给老师看的「日常维护指引」

对于班级主页、课程网站等需老师后续自行更新的网站，在设计蓝图里注明「哪些模块易于自行更新、更新时需准备什么材料」。

## 十、通用交付物：一页纸「网页设计蓝图」模板

本域向「实际建站（生成真实静态网页）」交付的标准产物，是以下「设计蓝图」。它是教育内容与模块设计部分，落地时由建站能力据此实现：

```
【网页设计蓝图】

1. 网站类型：（班级主页 / 课程网站 / 作品展示 / 活动报名 / 教学小工具 / 组合型）
2. 目标用户：（谁看 / 谁操作 / 学段 / 使用设备场景）
3. 一句话定位：（这个网站存在的核心目的）
4. 风格基调：（视觉语气 + 对应学段建议，参考方法论⑤）
5. 页面结构（模块清单，按优先级标注 P0/P1/P2）：
   - 模块名称｜内容要素｜教育设计要点｜优先级
6. 关键互动组件设计：
   - 组件名称｜交互逻辑｜公平性/安全性设计｜适用规范（引用方法论④）
7. 未成年人信息与内容安全提示：
   - 涉及信息类型｜建议的最小化/脱敏方式｜是否需要监护人知情同意提示
8. 非技术用户说明设计：
   - 面向老师的实现方式决策建议（如涉及）
   - 面向学生/家长的页面内操作引导要点
   - 面向老师的日常维护指引（如涉及）
9. 素材清单（需要用户提前准备的内容）：
   - 文字类｜图片类｜名单/表格类｜视频类
```

## 十一、写完必查：自检清单（8 问）

1. 是否说清「给谁看、谁操作、核心任务是什么」，而不是直接套通用模板？
2. 每个模块是否都有清晰的教育设计理由，而不是「好看就放」？
3. 涉及点赞/留言/评分类互动时，是否设计了防止网络欺凌和恶性攀比的机制？
4. 涉及表单/报名时，是否遵循信息最小化原则，没有多收集无关信息？
5. 涉及学生照片、姓名、成绩等信息时，是否给出了展示范围和脱敏建议？
6. 移动端首屏内容优先级是否清晰标注，而不是简单说「要适配手机」？
7. 是否为非技术用户设计了「怎么用/怎么搭」的说明？
8. 是否明确告知静态网页的技术边界（无服务器/数据库/后台），不承诺超出能力范围的功能？

## 十二、五类场景深度案例速查（完整流程见综合案例）

| 案例 | 典型需求 | 核心架构型 | 关键设计要点 |
|---|---|---|---|
| 班级主页 | 「做班级主页，展示公约、风采、荣誉墙、相册，青春活泼，手机电脑都能看」 | 型 1 | 第一人称「我们」语气；风采展示人人有位置；荣誉类型多样化；维护指引降低后续门槛 |
| 课程网站 | 「初中物理课程网站，按章节组织知识点、微课、练习，能自学」 | 型 2 | 首页做「课程地图」；知识点强制含生活化例子；练习反馈给「错因提示」 |
| 作品展示站 | 「学生作品在线展示，能传作文/绘画/手工，能点赞留言」 | 型 3 | 默认「最新优先」；留言「先审后显」或过滤+举报；投稿须知写清展示范围 |
| 报名网站 | 「班级活动报名，家长选时段填信息，后台看名单」 | 型 4 | 家长关心信息前置加粗；时段名额透明；名单看板权限边界；给出三种实现路径决策 |
| 小工具网页 | 「随机点名分组工具，录入名单后一键抽人、自动分组」 | 型 5 | 批量粘贴录入；结果区带仪式感；历史记录可查；规则默认值教育友好 |

> 完整案例的澄清定位、模块清单（含 P0/P1/P2）、互动组件设计、隐私提示与「怎么用/怎么搭」说明，可参照本方法论的逐案展开思路在对话中落地。
